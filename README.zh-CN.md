# LyricsBar — 只要任务栏歌词

> 当前版本 **1.4.4**：修好网易云**同名曲下"放 A 显示 B 的歌词"**（歌手从软条件改成硬条件，对不上就不按 id 取词）。
> 上一版 1.4.3 修好了纯音乐 / 无歌词时整条栏消失（现在会留下封面与曲目信息块）。

从 [AF Media Bar](https://github.com/Fervent-Tempo/AF-Media-Bar) 抽离出来的**极简任务栏歌词工具**。
只做一件事：把当前播放歌曲的歌词显示在 Windows 任务栏上，逐字跟唱。

原项目的音频控制、频谱、性能组件、音量控制、12 个设置页、更新模块、多语言等全部**不包含**。本项目只保留基础的上一首/下一首与播放/暂停控制。

> 文档：本文件（用法与排查）与 `CHANGELOG.md`（版本历史）；依赖与来源声明见 `THIRD-PARTY-NOTICES.md`，许可见 `LICENSE`。
> 维护者用的交接笔记、状态说明与渲染层改造记录**不在本仓库里**（它们是内部文档），本文件是唯一的用户文档。

## 它做什么

- 从系统媒体会话（SMTC）读取当前播放曲目，任何走系统媒体控制的播放器都能用
- 联网取词：网易云 / QQ 音乐 / 酷狗 / 汽水 / LRCLIB 五个来源并发检索
- 解析 LRC / YRC / QRC / LYS，支持**逐字（音节）同步**
- 把歌词栏停靠进任务栏，宽度跟随歌词内容自动伸缩
- **显示歌曲封面**（取自播放器上报的 SMTC 封面；无封面时退化为曲名首字母色块）
- **停靠位置可选靠左 / 居中 / 靠右**，并可在此基础上加偏移量微调
- **歌词字体可选**（下拉列出系统已安装字体，也可直接输入字体名）
- **封面右侧的曲目信息块**：把当前曲名与歌手显示在封面右边，歌词在它右侧；曲目信息取不到时整块自动收起，不占宽度。没有歌词时也可用**曲名与歌手**兜底（配合封面；可在设置中关闭）
- 可选**鼠标操作**：鼠标移到歌词栏上时，控制按钮（上一首 / 播放暂停 / 下一首）**浮在歌词上方**一块磨砂玻璃底板上（把身后的歌词模糊掉），滚轮切歌，播放器不支持的操作会置灰
- **播放 / 暂停**（走 SMTC `TryTogglePlayPauseAsync`，播放器未提供该能力时按钮置灰）
- 逐字擦亮、双行（默认顺序「翻译 → 音译 → 下一句」）、繁简转换、底部播放进度条
- **歌词由程序自己绘制（原生 WPF 自绘），不再内嵌浏览器**：只有一个 `LyricsBar.exe` 进程。
  实测任务管理器里的"内存"（私有工作集）：**播放中约 57MB、空闲约 28MB**（v1.4.0 之前是 155MB 上下 + 一整套 `msedgewebview2` 子进程）；
  设置里仍可切回网页引擎兜底
- **网易云音乐的播放位置也跟得上**：它的系统媒体接口上报的位置恒为 0，本程序改为只读地读它进程内存里那个真实位置，所以**拖动进度条、暂停、随机切歌都会同步**（读不到时静默退回本地计时，其它播放器不受影响；原理与代价见下文）
- 对齐可选**左 / 居中 / 右 / 左右分离**（左右分离＝两行仍上下排，但主行靠左、第二行推到最右）
- **文字颜色**可填任意 `#RRGGBB` 或颜色名（如 `White`、`#FFE082`）
- 托盘图标 + 单页设置

## 系统要求

- Windows 10 1809 或更新（x64）
- 发布包自带 .NET 10 运行时，**不需要另外装 .NET**（发布目录只有一个约 178MB 的 exe）
- **默认不再需要 Microsoft Edge WebView2 Runtime**：歌词由程序自己绘制。只有把设置里的「歌词渲染」切回「网页（WebView2）」时才需要它（Win10 1809+ 通常已内置；缺失时装 Evergreen Runtime）

> 关于体积与内存的取舍：那个 178MB 是**刻意**的——单文件开压缩能压到 75MB，
> 但压缩包会在启动时整包解压进内存，常驻内存翻两三倍（155MB → 57MB 的差距主要就是它）。
> 想换成小体积：加 `-p:SelfContained=false` 重新发布会得到约 30MB 的 exe（内存几乎一样，但目标机要装 .NET 10 桌面运行时）。

## 快速开始

### 方式一：用现成的单文件程序

```
dist/LyricsBar.exe
```

双击即可。程序启动后不会显示主窗口，只在任务栏出现歌词栏、在托盘出现一个音符图标。
托盘图标**左键单击打开设置**，右键打开菜单。设置窗口是 Win11 风格的单页卡片式界面（[界面预览](docs/settings-preview.png)）。鼠标操作默认开启：控制按钮只在鼠标移入歌词栏时出现（平时收起，不挡任务栏图标），上滚切上一首、下滚切下一首，单击三个按钮分别是上一首 / 播放暂停 / 下一首。播放器未通过 SMTC 提供某项能力时，对应按钮置灰。需要让鼠标点击继续落到任务栏时，可在设置中关闭「鼠标操作」，恢复点击穿透。

播放器不上报时间轴时（网易云音乐），托盘菜单还有三项手动同步：**回到本首歌开头**、**快退 10 秒**、**快进 10 秒**。网易云的真实位置现在由内存通道自动跟随（见下文），所以这三项只在通道读不到、退回本地计时时才有用。

### 方式二：从源码构建

需要 **.NET 10 SDK**（`global.json` 未锁定，10.0.2xx 及以上均可）。

```bash
# 调试运行
dotnet run --project src/LyricsBar/LyricsBar.csproj

# 发布单文件（本仓库已发布好的产物在 dist/LyricsBar.exe）
dotnet publish src/LyricsBar/LyricsBar.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -o dist

# 想要小体积（约 30MB，需要目标机装 .NET 10 桌面运行时）
dotnet publish src/LyricsBar/LyricsBar.csproj -c Release -r win-x64 -p:SelfContained=false -p:PublishSingleFile=true -o dist-fx
```

> 发布配置里 `EnableCompressionInSingleFile` 是**故意关掉**的，别顺手改回 `true`：
> 它把 exe 从 178MB 压到 75MB，代价是常驻内存翻两三倍（见上方"体积与内存的取舍"）。

## 排查问题

程序自带命令行自检，会检查运行环境并把结果写进日志：

```bash
LyricsBar.exe --diagnose
LyricsBar.exe --diagnose "晴天" "周杰伦"     # 指定曲目试取歌词
```

**自检可以在程序运行时执行**，不需要先退出。

自检会输出：系统与 .NET 版本、WebView2 运行时版本、发现的每一块任务栏（含 DPI 缩放）、
媒体会话是否可用、**SMTC 原始时间轴字段**、播放位置是否在推进、**网易云内存通道的扫描计数与锁定耗时**、
当前曲目、一次完整的取词结果
（来源、匹配分、格式、同步级别、行数、前 5 行与逐字片段数），以及**取词 + 投影的最终帧**
（是否可见、行下标、当前行文本、当前行译文与翻译模式）、逐行的「第二行样例」（那一行最终会选翻译、音译还是下一句）。最后一项是判断"歌词为什么不显示"的关键。

还有一个诊断开关：

```bash
LyricsBar.exe --no-dock     # 不停靠进任务栏，以普通窗口运行，用于分离"渲染问题"与"停靠问题"
```

### 核对歌词观感（改渲染层之后）

歌词是手写绘制的，排版、逐字擦亮、水平滚动、换行上滚改坏了不会有任何编译期信号。这条命令把每种情形各画一张 PNG：

```bash
LyricsBar.exe --render-preview               # 输出到 %TEMP%\lyricsbar-preview
LyricsBar.exe --render-preview D:\out\lyr    # 或指定目录
```

会输出 13 张图：居中 / 左右分离 / 译文对 / 超长行水平滚动 / 字距 20% / 靠左无封面 / 截断省略号 / 纯音乐留栏 / 悬停磨砂前后 / 上滚三帧。
改完 `LyricsNativeRenderer.cs` 跑一遍对着图看，比反复开关程序快得多。和 `--diagnose` 一样，它不创建窗口、可以直接在程序运行时执行。

**日志位置**：`%LOCALAPPDATA%\LyricsBar\lyricsbar.log`（超过 1MB 自动清空重写）
**设置位置**：`%LOCALAPPDATA%\LyricsBar\settings.json`

### 歌词不显示？

按这个顺序查：

1. 托盘菜单里「显示歌词」是否被勾掉
2. 先播放一首歌——没有媒体在播放时歌词栏是隐藏的
3. 跑 `LyricsBar.exe --diagnose`，重点看这几行：
   - `投影结果: IsVisible=...` —— 若为 `False`，说明**取词成功但没能定位到歌词行**
   - `SMTC 原始时间轴` —— 若 Start/End/Position 全是 0，说明这个播放器不上报进度
   - `位置推进检查` —— 三次读数应该在稳定增长
   - `网易云内存位置通道` —— 用网易云时应显示「已锁定（用时 x 秒）」；没锁上就会退回本地计时（歌词仍在，只是拖过进度条后要手动同步）
4. 日志里应出现「已启用原生歌词渲染器（不再起 msedgewebview2 子进程）。」。若没有、而是走了网页引擎，检查设置里的「歌词渲染」；若走网页引擎且歌词栏一片空白，勾上「兼容模式」再重启程序（见下）

### 关于歌词渲染

歌词**默认由程序自己绘制**（原生 WPF 自绘）：没有内嵌浏览器、没有额外进程，内存占用最低。
设置里的「歌词渲染」可以切回**网页引擎（WebView2）**，它会额外拉起一整套 `msedgewebview2` 子进程，
内存高得多，保留它只是为了逐项对拍观感与出问题时兜底。切换后需要点一次「重新停靠到任务栏」生效。

网页引擎下，在**虚拟机、远程桌面、部分受限企业终端**上，WebView2 的子进程可能反复崩溃，
表现为「歌词栏位置正确但一片空白」或干脆不出现。崩溃分两类，需要不同的处理：

| 现象 | 原因 | 处理 |
|---|---|---|
| GPU 进程崩溃 | 显卡/驱动不可用 | 关掉 GPU（软件渲染）即可 |
| 工具进程也崩溃 | **Chromium 沙箱无法初始化** | 必须连沙箱一起关 |

程序会**自动逐级降级**：先试默认 → 失败换 `--disable-gpu` → 再失败换 `--disable-gpu --no-sandbox`。
每一级都会写进日志。整个过程约 10 秒。

**降级级别会被记住。** 某一级真的跑通之后，程序把它写进设置，下次启动直接从这一级开始，
不再重复"崩溃—重建"的过程。所以第一次启动可能要等约 10 秒，之后就是 4～5 秒。

如果连降级都没跑通，程序也不会一直卡着：文档 15 秒内没加载完成就按失败处理，
**先按同一级别重试一次**（最常见的原因不是参数不对，而是上一个实例的 WebView2 进程还没退干净、
仍占着数据目录，等一会儿用同样的参数重来就好了），再不行才继续降级。

如果每次启动都要先崩两次才正常，直接在设置里勾选（这两项**只对网页引擎有效**）：

- **强制软件渲染** —— 跳过第 1 级
- **兼容模式：同时关闭沙箱** —— 直接使用最重的一级（受限环境推荐）

> 这两个开关都取消勾选时，程序会**忘掉**记住的降级级别，回到默认渲染路径。
> 换了显卡驱动或系统环境之后想重新试一遍默认路径，用这个方式重置。

> 关闭沙箱的安全性说明：歌词页是本程序内嵌的自包含文档，不导航到任何外部地址，
> 且已关闭 DevTools、右键菜单与状态栏，没有不可信网页内容可供利用。

## 已知限制

- **只支持横向任务栏**（屏幕顶部或底部）。竖向任务栏未实现
- **只有简体中文界面**（原项目支持四种语言）
- **只提供上一首/下一首与播放/暂停控制**，不支持音量等操作；播放器必须通过 SMTC 提供相应能力，否则按钮置灰
- **鼠标操作默认开启**，歌词栏会拦截其覆盖范围内的任务栏点击和滚轮；在设置中关闭后恢复点击穿透
- **无歌词时的曲目信息须等待检索完成**；检索期间整条栏仍然留在任务栏上（只剩封面），不会先闪没再出现
- **第二行的来源顺序可调**：设置里的「第二行优先」有三档预设（翻译→音译→下一句 / 音译→翻译→下一句 / 下一句→翻译→音译），默认翻译优先
- 歌词栏位置由「靠左 / 居中 / 靠右 + 偏移量」决定，**不跟随任务栏图标避让**（原项目有完整的避让算法），
  所以歌词栏可能压在任务栏图标上；用偏移量躲开即可
- 多显示器时只使用主显示器任务栏
- **网易云的播放位置靠只读它进程内存拿到**（唯一能跟随拖动进度条的办法，原理见上文）：换歌后重新锁定约 6 秒、
  网易云大改内存布局时可能读不到——这两种情况都会**静默退回本地计时**，此时需用托盘菜单的三项手动同步推回
- **歌词默认由程序自己绘制**，不再内嵌浏览器；设置里可以切回网页引擎（WebView2）兜底，但那条路会额外拉起一整套浏览器子进程，内存高得多
- **原生渲染器没有频谱场景**：旧版网页前端里那套"无歌词时柱子律动"的频谱，宿主从来没有真正触发过，属于死代码，因此没有搬过来
- **字距大于 0 时，原生渲染器的拉丁文排版与浏览器略有差异**（WPF 没有字距属性，只能逐字排布）；默认字距为 0 时走整行绘制，与浏览器观感一致
- 发布包未签名，Windows 会提示「未知发布者」

### 停靠位置的偏移量怎么算

设置里的「位置偏移」对三种对齐方式含义略有不同：

| 对齐 | 偏移量的含义 | 例子（任务栏宽 2560px，歌词栏宽 180px，150% 缩放） |
|---|---|---|
| 靠左 | 距任务栏左边缘的间距 | 偏移 0 → 左边界 0px；偏移 120 DIP → 左边界 180px |
| 居中 | 在正中基础上的左右平移 | 偏移 0 → 左边界 1190px；偏移 120 DIP → 左边界 1370px |
| 靠右 | 距任务栏右边缘的间距 | 偏移 0 → 左边界 2380px；偏移 120 DIP → 左边界 2080px |

偏移量单位是 DIP，会按显示器缩放换算成物理像素（上表是 150% 缩放，120 DIP = 180px）。
三种方式都会把结果**夹在任务栏范围内**，偏移量再大也不会把歌词栏推出屏幕。

### 播放进度对不上的情况（重要）

**网易云音乐的 SMTC 时间轴是恒零的**——Start / End / Position / MinSeek / MaxSeek 全是 0，
`LastUpdatedTime` 是 1601-01-01。也就是说它根本不通过系统接口上报播放到哪了。
它的窗口对 UI Automation 只暴露 3 个空 Pane（一个滑块都没有），也没开 CEF 调试端口。

因此从 v1.3.3 起，本项目**只读地读它进程内存里的真实播放位置**（自己的实现，不是移植）：程序启动后约 5 秒
锁定一簇每秒 +1 的地址，之后每 400 毫秒读一次。于是下面这两种情况在网易云上也不再跑偏：

- **程序启动时歌已经播到一半** —— 锁定后立刻取到真实位置
- **手动拖动进度条** —— 位置跟着跳；暂停时冻结，恢复播放继续走

代价与边界一并说清楚：

- 这是**读另一个进程的内存**，只用 `PROCESS_VM_READ`：不写入、不注入、不改动网易云的任何数据，也不依赖写死的偏移表，
  靠的是"播放位置是内存里一个每秒 +1 的浮点数"这一实测事实。网易云大改内存布局后可能失效，但失效只是
  **静默退回本地计时**——不会崩，也不会影响其它播放器。
- 退回本地计时的那几秒（换歌后重新锁定约 6 秒，或内存通道读不到时），"启动时已播一半 / 拖过进度条"这两种老症状会短暂出现；
  此时仍可用托盘菜单的「歌词同步：回到本首歌开头 / 快退 10 秒 / 快进 10 秒」手动推回。注意内存通道在位时
  这三项**点了不会有反应**（位置每 400 毫秒就被真实值覆盖），它们只是读不到时的兜底。
- **进度条本身不受影响**——拿不到时长时改用歌词最后一行的结束时间当刻度。

能正常上报时间轴的播放器（QQ 音乐、酷狗、Spotify、浏览器等）不受此影响，会直接采用系统上报的位置。

### 关于前奏

位置早于第一句歌词时（前奏），歌词栏会**显示第一句**而不是留空。否则十几秒的前奏会让整条栏空着，
看起来像"歌词没取到"。

- `LyricsSecondaryLinePolicy` —— 默认顺序由「下一句 → 翻译 → 音译」改为「翻译 → 音译 → 下一句」
- `LyricsWebViewRenderer` —— 新增可选的 WebView2 启动参数、GPU/工具进程崩溃的计数阈值、封面消息通道，以及曲目信息（`trackInfo`）与磨砂浮层（`overlay`）两条消息通道
- `LyricsDurationPolicy`（新增文件）—— 时长优先取播放器上报值，没有则退到歌词末行的结束时间，供进度条当刻度
- `Web/Lyrics/**` —— 新增封面右侧曲目信息块（`index.html` 一块 DOM、`style.css` 网格加一列并用 `--track-info-width` 收起、`app.js` 一个 `setTrackInfo`）、控制按钮的磨砂浮层（`#overlayBackdrop` + `--overlay-width`）、以及「左右分离」对齐（`.layout[data-text-alignment="Split"]`），其余保持上游一致

其余移植文件保持与上游一致。

### 新写的部分

- **原生歌词渲染器**（`Classes/Services/Lyrics/Presentation/LyricsNativeRenderer.cs`，v1.4.0）：把歌词从"内嵌浏览器"改成
  "程序自己绘制"。两行歌词、换行上滚（单行 560ms / 译文对 760ms）、逐字擦亮（两遍绘制 + 渐变不透明度遮罩，等价于 CSS 的
  `mask-image`）、超长行按 65% 锚点水平滚动、封面双图交叉淡入淡出、封面右侧曲目信息块、悬停磨砂（原生 `BlurEffect`，
  只糊歌词那两块）、左/居中/右/左右分离四种对齐、物理像素对齐。它按 `app.js` / `style.css` 的常量重写观感，不含上游代码；
  两种渲染器由 `ILyricsRenderer` 接口统一，设置项 `LyricsRendererEngine` 切换。
- SMTC 媒体读取（原项目 1098 行的 `MediaSessionService` → 精简实现），
  含**播放器不上报时间轴时的本地计时兜底**与手动同步；另有独立的 `MediaTransportService` 负责上一首/下一首与播放/暂停
- **网易云播放位置的只读内存通道**（`Classes/Interop/ProcessMemory.cs` + `Classes/Services/NeteasePositionService.cs`，原项目没有对应实现）：只读地扫它进程内存里那簇每秒 +1 的浮点数，三遍筛选（值域粗筛 → 隔 2 秒看推进 → 单点复核），
  锁定后每 400 毫秒读一次；读不到就静默退回本地计时，全程不写它的内存、不依赖偏移表
- **封面读取**（`CoverArtLoader`）：把 SMTC 的封面流解码后缩到 128px、按 JPEG 重编码成 data URI，
  约 10 KB 随快照一起下发，避免在任务栏上为一个 34px 的小图传整张原图
- 应用图标统一加载（`AppIcon`）：嵌入的 `LyricsBar.ico` 同时供 exe 资源区、托盘与设置窗口标题栏/页头使用
- **网易云的按 id 精确取词**（`Classes/Services/NeteaseQueueService.cs`；原项目靠内存偏移硬读 id）：只读它的播放队列文件
  （`WebData/file/playingList` 与 `fmPlay`，只读、不写、不注入），按"曲名（含别名）归一化后完全相等 **且歌手对得上**"
  反查当前曲目的歌曲 id，交给 `Netease` 来源按 id 取词（命中即匹配分 100）。**歌手是硬条件**（v1.4.4）：歌手对不上、
  或队列里同名曲不止一首时一律不给 id、退回搜索路径——同名曲里随便挑一首，正是"放 A 显示 B 的歌词"的来源
- 取词协调器（换歌取词、同曲不重取、按策略清缓存）
- 任务栏窗口与尺寸计算（原项目的 `LayoutRenderEngine` 有 461 行，这里只需按歌词文本量宽，
  再加上封面占位与三种对齐方式）；控制按钮浮层在**歌词区**居中、三枚按钮 34 DIP
  （歌词区左边界由「排版内边距 4 + 封面 36 + 间距 8」算出，与前端网格的列宽一致，因此不需要额外通信就能对齐）
- 设置模型（原 `SettingsManager` 被引用 334 次，这里收敛为单页设置 + JSON）
- 托盘图标、设置窗口、命令行自检
